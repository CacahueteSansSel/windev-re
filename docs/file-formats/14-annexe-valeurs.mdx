## Comment lire cette annexe

Cette annexe illustre un profil de schéma associé au projet fictif `SuperNoteExtra/SuperNoteExtra.wdd`. Le profil de buffer reconstruit `H` mesure 15 821 octets, le GUID d’analyse fictif est `54077D9E89F753879ECE3503D29F691E` et la génération d’exemple vaut 24.

Les tableaux séparent la position du début de la rubrique `R` et la position `Q` du code de type après les quatre CString. La largeur binaire du code est toujours **16 bits**, même lorsque la donnée métier décrite occupe 64 bits.

| Colonne | Signification |
| --- | --- |
| Début `R` | Tag 20 de la description de rubrique dans `H` |
| ID | Identifiant interne enregistré sur 32 bits |
| Code de type à `Q` | Premier octet du `u16` de type ; les flags suivent à `Q + 2` |
| Type interne | Code binaire, avec sa valeur décimale et hexadécimale |
| Flags | Valeur entière brute sur 32 bits ; bits non nommés arbitrairement |
| Taille | Valeur `u16` à `Q + 7` ; ne vaut pas nécessairement un nombre de caractères |
| Autre taille | Valeur `u16` à `Q + 9`, exposée comme taille de stockage par le lecteur ; unité complète non certifiée pour chaque type |

Les rubriques suivent l'ordre de l'index de leur table. La signification des codes figure dans le [chapitre WDD](./10-wdd-analyse.mdx).

## Distinction entre valeur et sémantique

Le lecteur restitue les libellés et masques tels qu’ils sont stockés ; les valeurs de cette annexe illustrent leur représentation dans le projet fictif. Un masque `999` ne suffit pas à définir toutes les contraintes d'une rubrique. Un flag à 1 n'est pas renommé « clé primaire » sans preuve sur le champ et son contexte.

Les champs `COULEUR` et `ICONE`, par exemple, portent le code interne 26 et le code public 22 dans la référence JSON. Cette correspondance est vérifiée pour ces rubriques ; elle ne remplace pas une spécification exhaustive de tous les types et combinaisons de flags WINDEV.
