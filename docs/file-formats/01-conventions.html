Conventions, types et offsets

Exemples fictifs​

SuperNoteExtra désigne le logiciel fictif de prise de note ; SuperMailExtra, le logiciel fictif de client mail. Un nom de logiciel, un chemin, un titre, une date ou un GUID d’exemple ne permet pas d’identifier un projet réel.

Les tableaux de sections et de compression conservent des profils numériques issus de l’étude des formats. Les extraits textuels sont des exemples autonomes, adaptés aux noms fictifs. Ils ne décrivent pas une reconstruction binaire complète d’un même fichier avec toutes ses régions opaques. Pour un fichier concret, le répertoire PCS, les longueurs des chaînes et les pointeurs internes donnent les positions effectives.

Dans chaque extrait, les longueurs dépendent des octets réellement affichés. Les références WDP consécutives utilisent position_suivante = position_courante + C + 20. Les chemins et titres d’illustration peuvent avoir été raccourcis pour conserver la largeur des champs ; les CString de noms de fichiers et les chaînes encadrées des noms de logiciels ont des tailles adaptées.

Les GUID sont fictifs mais conservent leurs 32 chiffres hexadécimaux, soit 33 octets avec NUL. Les empreintes de fichiers du corpus d’étude ne sont pas publiées ; une empreinte doit être calculée sur les octets du fichier dont on souhaite vérifier l’identité.

Unités et numérotation​

Toutes les positions sont zéro-indexées. Le premier octet d'un fichier se trouve à l'offset 0. Les tailles de champs, de blocs et de sections sont données en octets, sauf mention explicite de bits.

Les sections sont numérotées depuis 0. Une référence à « section 2 » désigne la troisième entrée du répertoire.

Le type binaire du code d'une rubrique est u16, même si la rubrique décrit une valeur métier sur 64 bits. Par exemple, le nombre 24 occupe deux octets dans la description et désigne un identifiant automatique dont la taille métier observée est huit octets.

Ordre des octets​

Tous les entiers multioctets décrits ici sont lus avec l'octet faible en premier :

Octets : 1F 00
Lecture u16 : 31

Octets : 59 01 00 00
Lecture u32 : 345

Octets : 9F 02 00 00 00 00 00 00
Lecture u64 : 671

L'ordre des bits du LZW est un problème distinct de l'ordre des octets des entiers. Les deux doivent être appliqués séparément.

Conversion des offsets​

Pour un champ conservé tel quel dans une section :

offset_dans_le_fichier = début_de_section + offset_dans_la_section

Pour une enveloppe LZW :

début_du_flux_encodé = début_de_section + position_enveloppe + 11

Cette formule localise le flux encodé. Elle ne localise pas un octet quelconque de la sortie décompressée : aucune correspondance affine générale n'existe entre les octets source et les octets décodés.

Dans le WDD, tous les pointeurs internes décrits dans cette documentation s'appliquent au buffer H, qui inclut les quatre octets 60 00 1D 06 réinsérés après décompression.

Champs à longueur variable​

Une CString ou une chaîne encadrée déplace les champs suivants. Il faut utiliser une formule ou un curseur, et non recopier l'offset d'un exemple :

p = début_de_la_chaîne
lire_la_chaîne
p = premier_octet_après_la_chaîne
lire_le_champ_suivant_à_p

Les caractères accentués peuvent occuper plusieurs octets en UTF-8. La longueur en caractères n'est pas la longueur binaire.

Alignement et données opaques​

Le répertoire PCS commence à 81 et ses entrées mesurent cinq octets. Il n'impose donc pas un alignement sur 2, 4 ou 8 octets. Les lectures doivent fonctionner à toute position.

« Inconnu » ne signifie ni « inutile » ni « réservé ». Les octets inconnus doivent être conservés si l'on souhaite poursuivre l'analyse ou tenter une réécriture. L'encodage d'un booléen, d'un enum, d'un masque de bits ou d'un identifiant ne doit pas être déduit seulement d'une valeur 0 ou 1.
