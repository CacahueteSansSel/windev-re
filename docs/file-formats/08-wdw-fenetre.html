Format WDW : fenêtre

Exemples fictifs. Les noms, chemins et identifiants applicatifs sont anonymisés. Les cartes de sections sont des profils numériques de référence ; les extraits textuels sont des exemples autonomes. Voir les conventions des exemples.

Section 0 : identité​

Comme dans le WDP et le WDG, la section 0 commence par un mot brut de quatre octets égal à 7, puis une chaîne encadrée de nom à +4. Des métadonnées et un chemin de projet suivent.

Pour FEN_Journal, la section commence à 241 et la chaîne de nom à 245.

Section 1 : enveloppe des propriétés​

Dans FEN_Journal, l'enveloppe LZW commence à +28. Les 28 octets précédents ne sont pas entièrement interprétés :

Cette carte n'est appliquée que si le descripteur vaut 610 et que le nom racine correspond à la fenêtre. Le mot 610 ne doit pas être assimilé à un nombre de champs.

Les noms peuvent être modifiés par le développeur. Un contrôle portant un nom sans ces préfixes peut exister ; un nom ressemblant à un préfixe n'est pas une preuve de type. La hiérarchie parent/enfant et toutes les propriétés de chaque contrôle ne sont pas décodées.

Code et données auxiliaires​

La section 2 produit 288 361 octets de code et métadonnées dans FEN_Journal. Les propriétaires d'événements permettent de retrouver certains noms de contrôles et procédures locales ; voir le chapitre WLangage.

Les sections 3 et 4 sont décompressées, mais toutes leurs structures internes ne sont pas interprétées. La section 4 produit notamment 3 540 482 octets. Cette grande taille ne permet pas, à elle seule, de conclure que tout ce buffer est un bitmap ou une image particulière.

Limites​

Le titre et les dimensions du descripteur 610 sont identifiés. Les coordonnées des champs individuels, les styles, les liaisons de données, les images, les plans et la hiérarchie complète restent à cartographier. Les régions inconnues sont conservées dans les buffers décodés.
