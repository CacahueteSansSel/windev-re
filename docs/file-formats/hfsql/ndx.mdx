Le NDX accélère les parcours et les recherches. L’étude reconnaît son répertoire terminal et ses descripteurs de 60 octets ; elle ne reconstitue pas encore les clés ni le parcours du B-tree.

Les positions sont exprimées en **octets**. Les inconnues sont indiquées comme telles ; voir les [conventions](../conventions.mdx).

## Structure déterminée

Le type est `0x00070002`. Après l’en-tête commun, un compte et un pointeur annoncent un **répertoire terminal de positions sur 64 bits**. Le découpage a été vérifié sur les 160 NDX initiaux, représentant quatre contenus distincts, puis sur PERSONNE.ndx en WINDEV 28.

Les positions sont exposées comme débuts de régions/descriptions d’index. Le profil plat 31 du [cas jours et semaines](./cas-hfsql31.mdx) permet désormais de lire des clés en clair. Les comparateurs généraux, liens de pages et parcours B-tree restent inconnus.

```text
exiger I >= 119
exiger I + N × 8 = longueur_fichier
position[j] = lire_u64(F, I + j × 8)
exiger 119 <= position[j] < I
exiger les positions strictement croissantes
```

La valeur à 111 n’est pas une « taille du fichier moins 32 » universelle : 32 correspond seulement à quatre entrées de huit octets.

## API

```csharp
var index = NdxHfsqlIndexFile.Open(@"D:\Projet\SuperNoteExtra\RADFic.ndx");
Console.WriteLine(index.DeclaredIndexCount);
Console.WriteLine(index.DirectoryOffset);
foreach (int position in index.IndexDescriptorOffsets)
    Console.WriteLine(position);
ReadOnlyMemory<byte> region = index.ReadIndexRegion(0);
```

La bibliothèque valide les bornes et préserve les octets sans les traduire en clés ou en enregistrements FIC.

## Descripteur terminal de 60 octets

Les pointeurs du répertoire désignent des descripteurs de 60 octets dans tous les contenus NDX étudiés. Les types ci-dessous décrivent le découpage retenu ; ils ne prouvent pas les types employés dans le code source du moteur. Les entiers sont en petit-boutiste.

| Offset relatif au descripteur `D` | Taille | Type de lecture | API / commentaire |
| --- | --- | --- | --- |
| `+0` | 2 | `u16` brut | `RawWordAt0` ; rôle inconnu, pas de checksum validé |
| `+2` | 4 | `u32` | Longueur 60 ; valeur vérifiée à l’ouverture |
| `+6` | 4 | `u32` brut | `RawWordAt6`, vaut `0x01000000` dans les profils |
| `+10` | 4 | `u32` brut | `RawWordAt10` ; pas un compte de lignes établi |
| `+14` | 2 | `u16` brut | `RawWordAt14` ; pas un type de rubrique établi |
| `+16` | 8 | `u64` brut | `RawPointerAt16` ; `0xFFFFFFFFFFFFFFFF` dans les profils RAD |
| `+24` | 4 | `u32` brut | `RawLengthAt24` ; longueur observée d’une région dans PERSONNE |
| `+28` | 8 | `u64` brut | `RawPointerAt28` ; position d’une autre structure, y compris avant `D` |
| `+36` | 8 | `u64` brut | `RawPointerAt36` ; autre position physique |
| `+44` | 16 | `u32[4]` bruts | `RawTailWords` ; tous nuls dans PERSONNE |

`IndexDescriptors` expose ces champs. Les valeurs sentinelles des pointeurs bruts restent des `ulong` ; elles ne sont pas converties en adresses exploitables. Le lecteur ne suit pas ces pointeurs et ne leur attribue pas encore de rôle de racine B-tree, de liste libre ou de feuille.

Dans PERSONNE, le premier descripteur est situé à 5 034, tandis que `RawPointerAt28` vaut 135. **Le premier descripteur n’est donc pas nécessairement le début de l’index logique.** `ReadIndexRegion(i)` conserve son contrat historique : il renvoie les octets entre deux descripteurs consécutifs, ou jusqu’au répertoire terminal. Ce n’est pas une reconstruction des pages de l’index. Voir la [carte complète du cas PERSONNE](./cas-personne.mdx#ndx--descripteurs-et-régions).

`ReadFlatIndex(i)` expose un en-tête de 29 octets au tag 7, puis des clés de largeur fixe et deux références brutes par entrée. Le compte inclut une sentinelle tout à 1, retirée de la liste `Entries`. Les tableaux ont été recoupés avec tous les emplacements des deux nouveaux FIC, soit sept tableaux et 35 clés. Ce décodage ciblé ne s’applique ni aux NDX RAD opaques ni au profil PERSONNE 28.
