HFSQL 31 : jours fériés et semaines

Les quatre témoins sont deux couples FIC/NDX WINDEV 31. Leurs GUID correspondent aux tables JOUR_FERIE et SEMAINE_COURS du WDD initial. Les identifiants applicatifs restent anonymisés ; les noms génériques des tables sont conservés pour expliquer les correspondances.

Résultat de la comparaison​

CoupleFICNDXEmplacements FIC recoupésPas

semaine_cours1 662 octets8 553 octets135 octets

Les valeurs sont lisibles sans transformation. Les métadonnées initiales restent opaques. L’en-tête physique porte les modes nuls à 88 et 89, et 0x8000 à 86, comme PERSONNE. Cela ne constitue toujours pas un détecteur universel de mot de passe.

Le lecteur conserve donc un début et un nombre d’emplacements explicites. Les valeurs PERSONNE, après modifications/suppressions possibles, ne se réduisent pas aux mêmes égalités.

JOUR_FERIE : valeurs et clé composée​

Le WDD annonce cinq rubriques mais seulement quatre occupent une zone de valeurs dans le FIC. Pour l’emplacement i, S = 1763 + i × 70, avec i de 0 à 7.

Offset relatifPremier offset absoluTailleNom / typeCommentaire
S+01 7639Gestion brutePremier octet 0x10 dans les huit emplacements ; état non certifié
S+91 7728IDJOUR_FERIE, lecture i64 LEValeurs 1 à 8
S+171 7801JOUR, u8Jour du mois
S+181 7811MOIS, u8Mois
S+191 78251LIBELLE, CP1252 ZTaille déclarée 50, stockage 51 ; accents recoupés
AucunAucun0 dans le FICMOISJOUR, clé composéePrésente dans le schéma et l’index, pas comme valeur supplémentaire

Le profil WDD de MOISJOUR est RawTypeCode = 28, RawFlags = 0x1C, Size = 2, StorageSize = 4. Son suffixe typé commence à H[9028] ; l’octet à Q+31, donc H[9059], vaut 1. Il est exposé comme RawCompositeMarker. La rubrique binaire HASH du même schéma porte aussi le code 28 et les flags 0x1C, mais cet octet vaut 0 : les flags seuls ne distinguent donc pas ces deux cas.

IsCompositeKey exige le type 28 et ce marqueur à 1 ; le libellé devient CompositeKey. L’association du marqueur est recoupée sur MOISJOUR et reste une interprétation du profil étudié. Les autres rubriques binaires conservent leur type. Les composants et l’ordre de la clé sont vérifiés dans le NDX, pas reconstitués automatiquement par le lecteur WDD.

8 + 1 + 1 + 51 + 9 = 70. Ajouter les quatre octets de métadonnée de stockage de MOISJOUR donnerait 74, en contradiction avec le WDD et les répétitions du FIC. Le lecteur de disposition omet cette clé composée et ne crée pas une valeur synthétique dans Values.

SEMAINE_COURS : dates sur neuf octets​

Offset relatif à 1 627Offset absoluTailleNom / typeValeur lue

+171 6449DATEDEB, huit chiffres ASCII + NUL20260504

Le WDD confirme le code de type 14, une taille déclarée 8 et un stockage 9. L’API explicite Date8Z retourne une chaîne de huit chiffres, sans conversion en fuseau horaire ou en horodatage. Elle vérifie les huit chiffres et le NUL ; la validation du calendrier est laissée à l’appelant. Le format logique AAAAMMJJ est aussi décrit dans la documentation PC SOFT des requêtes, sans y préciser ce stockage physique de neuf octets.

Une entrée​

Offset dans l’entréeTailleTypeContenu
0Koctets[K]Clé, ordre binaire lexicographique non décroissant

Les deux références sont égales dans tous ces témoins. Elles correspondent à la fois aux identifiants et aux rangs physiques à partir de 1, car les identifiants sont ici continus et dans l’ordre. Leur nature exacte ne peut pas être distinguée sur ces seuls fichiers ; l’API conserve des noms neutres.

La dernière entrée contient uniquement des octets FF, clé et références comprises. Elle est validée puis exclue de Entries. Les 35 entrées retournées se répartissent en 4 × 8 + 3 × 1. Il n’y a pas 42 lignes métier : les mêmes valeurs sont indexées plusieurs fois et les sept sentinelles ne sont pas des lignes.

Les deux références restent en petit-boutiste, même quand la clé d’identifiant présente un ordre d’octets différent. Ne pas appliquer l’endianess des entiers FIC à tous les octets d’une clé d’index.

Pourquoi les chaînes brutes ne suffisent pas​

D’autres régions NDX contiennent des textes de dates, notamment des valeurs antérieures, avec un autre tag et un compte nul dans le profil observé. Elles ne sont pas parcourues par ReadFlatIndex. Extraire tous les motifs 2026... du fichier produirait des valeurs qui ne correspondent pas à l’unique emplacement de SEMAINE_COURS.

Utilisation de la bibliothèque 0.5.0​

var analyse = WddWindevAnalysis.Open("SuperNoteExtra.wdd");
var jours = FicHfsqlDataFile.Open("jour_ferie.fic");
var disposition = jours.CreateFixedRecordLayout(analyse, 1763, 8);
foreach (var ligne in jours.ReadFixedRecords(disposition))
    Console.WriteLine($"{ligne.Values["JOUR"]}/{ligne.Values["MOIS"]}");

var index = NdxHfsqlIndexFile.Open("jour_ferie.ndx");
var cleComposee = index.ReadFlatIndex(3);
foreach (var entree in cleComposee.Entries)
    Console.WriteLine($"{entree.KeyHex} : {entree.RawReference1}");

Le nom d’analyse ci-dessus est fictif ; utiliser le WDD 31 correspondant réellement aux GUID. Les dispositions vérifiées sont aussi livrées dans examples/jour-ferie-schema-layout.json et examples/semaine-cours-schema-layout.json.

ReadFlatIndex reste une méthode ciblée : version 31, mode brut 0, descripteur et en-tête conformes au profil, compte borné, sentinelle et ordre des clés vérifiés. Elle ne suit pas les liens du B-tree et refuse les NDX RAD opaques ou le profil PERSONNE 28. Les autres méthodes de lecture brute restent disponibles.
